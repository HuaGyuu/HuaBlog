# 面试常见问题

## redis 为什么那么快

redis 快的原因有一下几种：
1. 内存操作
2. 单线程操作，避免多线程竞争和上下文切换
3. io 多路复用，可以在只有一个线程的情况下，同时监听成千上万个客户端连接
4. 采用高效的数据结构和编码

## redis 持久化方式

redis 支持 RDB 和 AOF 两种持久化方式。

### RDB

RDB 是将当前进程中的数据生成快照保存到硬盘中的过程。

RDB 支持手动触发和自动触发两种：
- 手动触发：
	- save 命令，会阻塞 redis，直到 RDB 完成
	- bgsave 命令，fork 子进程完成 RDB 操作，只有在 fork 子进程期间会阻塞
- 自动触发：
	- 使用 save 相关配置， 如“save m n”。 表示 m 秒内数据集存在 n 次修改时， 自动触发 bgsave。在配置文件中配置
	- 如果从节点执行全量复制操作， 主节点自动执行 bgsave 生成 RDB 文件并发送给从节点
	- 执行 debug reload 命令重新加载 Redis 时， 也会自动触发 save 操作
	- 默认情况下执行 shutdown 命令时， 如果没有开启AOF持久化功能则自动执行 bgsave。

::: tip 提示
电脑上的进程并不是直接访问内存，而是通过一个**页表**来访问内存，页表将进程使用的虚拟地址映射到物理内存的地址。

fork 子进程并不是将内存中的数据复制一份，而是将原进程的页表复制一份，这样子进程也能够访问到真实的数据
:::

主进程会采用 copy-on-write 模式，由于主进程和子进程共享一片内存空间，当主进程收到修改指令时，会将相关的数据复制一份，并修改复制的数据。

### AOF

AOF 的持久化方案是记录每一次执行的命令，恢复数据时，只需要重新执行这些命令就行了。

这样相较于 RDB 会有一些问题，最明显的就是 AOF 文件的体积更大了，好在能够通过**重写** AOF 文件，实现压缩体积。重写也有手动和自动两种触发方式。

每执行一个写命令，都会将命令写入到缓冲区中。在缓冲区中的命令并不是安全的，有丢失风险，故需要将其在某个时间写入到硬盘中。主要有三种方案：
1. always：每执行一个写命令，都写入磁盘。性能最差，可靠性最高
2. everysec：每秒中写入到硬盘一次，性能适中，且最多丢失一秒数据。
3. no：不主动写入硬盘，写硬盘的操作由操作系统决定。


## 缓存相关

缓存主要有三个问题：缓存穿透，缓存击穿，缓存雪崩

### 缓存穿透

缓存穿透是指访问一条不存在的数据，由于数据不存在，所以就不在缓存中，每次都会访问数据库

解决方案：
1. 缓存空数据。当在数据库中查不到数据时，也要缓存一个空数据，这样下次就能走缓存了。不过缓存失效时间不宜太长
2. 加一层布隆过滤器，请求来了先通过布隆过滤器。布隆过滤器能够大致判断一条数据是否存在，有一定误差，布隆过滤器认为数据不存在那就一定不存在

::: tip 提示
布隆过滤器底层是一个比特数组，每一位初始化都是 0；存数据时，取数据的多个 hash 值，将对应的比特为置为 1。查数据时，经过同样的 hash 后，若对应的位数都是 1，那么数据可能存在，反之，数据一定不存在。
:::

### 缓存击穿

缓存击穿是指一个热点 key 过期，使得大量请求进入数据库。

解决方案：
1. 加互斥锁。当发现缓存过期时，只放行一个线程取进行缓存的重建，其余线程等待。当缓存重建完成，其余线程再返回缓存数据。
2. 设置为逻辑过期。当发现 key 逻辑过期时，第一个线程新开一个线程去重建缓存，而当前线程和之后再访问的线程都直接返回缓存数据。
3. 提前预热。流量高峰前，提前加载缓存并延长过期时间。

### 缓存雪崩

同时有大量 key 过期，或 redis 宕机，使请求到达数据库

解决方案：
1. 为过期时间添加随机值
2. 搭建高可用集群
3. 设置多级缓存，加一层本地缓存，如 Caffeine


### 双写一致性

双写一致性就是要保证数据库和缓存在修改数据时保持一致。可以在修改数据库的同时，删除缓存中的数据，这样便实现了一致性。

但这样还有一个问题，那就是究竟是先删缓存还是先改数据库。
- 如果先删缓存。假如线程 a 删除了缓存，这是轮到线程 b 执行，而线程 b 发现没有缓存，这是就去数据库查出就数据，存到缓存中。这时，a 恢复运行，并将数据库也进行了修改。此时，就出现了数据库与缓存不一致的情况
- 如果先改数据库。假设此刻缓存失效，线程 b 就去查询数据库，还没写到缓存，这时轮到了线程 a 执行，a 修改了数据库，并且将缓存删除。这时又轮到 b 执行，b 就将旧的数据写到了缓存中，出现了不一致。

综上，两种方式都有可能导致数据的不一致性，但先改数据库出现不一致的概率更小。

如果追求强的一致性，可以加上互斥锁，让读写串行。或者是加读写锁，在读接口加读锁，写接口加写锁，就能并发读，但串行写。


## 数据过期策略

redis 有两种数据过期策略：
1. 惰性删除：当读到这个键，发现过期了，才会删除。可能导致有些 key 永远不会被删除。
2. 定期删除：每隔一段时间，检查一些设置了过期时间的 key，如果过期了就删除。

redis 同时使用了这两种过期策略


## 数据淘汰策略

当 redis 达到内存上限时，就会执行内存淘汰策略。由 maxmemory-policy 参数控制，有八种策略：
1. `noeviction`：默认策略，不会删除任何数据，**拒绝所有写入操作**并返回客户端错误信息，只响应读操作
2. `volatile-lru`：根据 LRU 算法（最近最少访问）删除**设置了超时属性（expire）的键**，直到腾出足够空间为止。如果没有可删除的键对象，回退到 noeviction 策略
3. `allkeys-lru`：根据 LRU 算法删除键，不管数据有没有设置超时属性，直到腾出足够空间为止
4. `allkeys-random`：随机删除所有键，直到腾出足够空间为止
5. `volatile-random`：随机删除过期键，直到腾出足够空间为止
6. `volatile-ttl`：根据键值对象的ttl属性，删除最近将要过期数据。如果没有，回退到noeviction策略
7. `allkeys-lru`：根据 LFU 算法（最少频率使用）删除键，不管数据有没有设置超时属性，直到腾出足够空间为止
8. `volatile-lru`：根据 LFU 算法删除**设置了超时属性（expire）的键**，直到腾出足够空间为止


## 分布式锁

简单的分布式锁可以利用 setnx 命令实现。为了防止在线程还未执行完时就释放锁，可以加入看门狗机制，定期给 key 续期。如果要实现锁的重入，可以利用 hash 结构，field 是与线程有关的数据，value 是重入的次数。


## redis 集群

### redis 集群方案

redis 集群有三种方案：
1. 主从复制
2. 哨兵模式
3. 分片集群

### 主从复制

主从复制主要解决高并发问题。

将主节点与从节点的职责分开，主节点负责数据的写入，从节点负责数据的读取，主节点数据更改时，需要将数据同步给从节点

主从同步有几个重要的属性：
1. Replication Id：每一个 master 节点又有唯一的 Replication Id，slave 节点设置 master 时，也会继承主节点的 Replication Id。主节点可通过从节点的这个值判断是否是第一次同步
2. offset：repl_baklog 文件的偏移量，值是不断增大的，通过主从节点的 offset 的不同，来知道同步哪些数据给从节点。

**全量同步**主要发生在主从第一次复制，流程：
1. 从节点执行 slaveof 命令建立连接
2. 主节点获取到从节点的 Replication Id 和 offset，判断是否是第一次复制
3. 是第一次复制，主节点会将其 Replication Id 和 offset 发送给从节点
4. 主节点执行 bgsave，生成 RDB 文件，并发送给从节点
5. 期间，执行的新命令会记录到 repl_baklog 文件中，并不断增大 offset
6. 从节点收到 RDB 文件后，情况自身数据，加载 RDB 文件
7. 主节点根据两者 offset，将 repl_baklog 中的数据发送给从节点
::: tip 提示
repl_baklog 实际是一个环形数组，当从节点的复制进度与主节点的进度差距过大，超过数组的长度时，就会进行全量复制
:::


**增量同步**主要发生在数据变化后，或从节点重启后，流程：
1. 主节点获取到从节点的 Replication Id 和 offset，判断是否是第一次复制
2. 不是第一次，主节点就依据主从间的 offset，发送对应的数据给从节点


### 哨兵模式

哨兵模式主要解决高可用问题。

哨兵主要有三个作用：
1. 监视。监视主节点和从节点的健康状态
2. 故障转移。主节点故障后，会选取从节点称为新的主节点。原主节点恢复后，也以新主节点为主
3. 通知。故障转移时，会将最新消息推送给 redis 客户端

哨兵也是 redis 节点，通常会部署成集群，每个哨兵每秒都会向每个 redis 节点发送 ping 做心跳检测，如果对方超过一定时间没有回复，当前哨兵就会认为这个节点**主观下线**。当超过一定数量的哨兵都认为该节点主观下线，那么该节点就变成**客观下线**

如果客观下线的是主键点，那么就会进行故障转移。首先，哨兵间会通过 Raft 算法，从哨兵中选出一个领导者，然后会从从节点中选取一个节点作为主节点，选取的原则是：
1. 过滤掉不健康的节点（下线，失联）
2. 如果有优先级最高的节点，则选择它，否则继续
3. 选择偏移量 offset 最大的节点
4. 如果偏移量也相同，就选择 runid 最小的节点

然后领导者就会将选出的节点设置为主节点，让其余从节点称为新主节点的从节点，同时也会关注原主节点，若其上线，让它称为新主节点的从节点

**脑裂问题**：哨兵由于种种原因联系不上主节点，认为主节点挂了，但主节点还能正常对客户端提供服务，而哨兵已经在从节点中选出了新的主节点，集群中就存在两个主节点。若此时原主节点与哨兵恢复了连接，那么哨兵会让原主节点成为新主节点的从节点，那么客户端在这期间向原主节点中写入的数据就会丢失。

可以通过两个参数缓解脑裂问题，不满足这两个条件，主节点就会拒绝写入
```
// 主节点至少要有一个从节点
min-replicas-to-write 1
// 主节点与从节点的复制延迟不能超过 10 秒
min-replicas-max-lag 10
```
由于脑裂时，原主节点大概率只是单个节点，满足不了上面两个条件，便会拒绝写入


### 分片集群

分片集群主要解决海量数据存储，和高并发写的问题。

分片集群由多个主节点构成，每个主节点能有多个从节点。分片集群不再需要哨兵，因为主节点间可以通过 ping 来做心跳检测，进而实现故障转移。而访问任意一个节点，都能够路由到正确的节点上

对于数据的存储，每个集群都有 16384 个槽，这些槽会分配给每个主节点，也就是每个主节点都拥有一定量的槽。当读写数据时，会依据 key 的 hash 值，算出对应的槽，将数据写入到持有这个槽的节点中，或从这个节点中读出值。当 key 中包含 `{}` 时，会将大括号内的字符作为有效部分计算 hash 值，否则就以整个 key 计算 hash 值。

集群扩容或者集群收缩时，也会以槽为单位来转移数据
